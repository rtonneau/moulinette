## Review Notes

Checked against the Acceptance Criteria:

- **New data structure and `Format` value.** `gui_state::ChargeCalibration { monitor_adc: u8, counts_per_uc: Option<f64> }` (new, `src/gui_state.rs`). `conversion::Format::ChargeNormalized` (new, `src/conversion.rs`) is registered in `name()` ("chg"), `ALL` (now 13), `FromStr` (via `ALL`, no alias needed) and `legacy_filename` (prefix "CH" — added a dedicated assertion in `unsupported_inventory_and_legacy_names` that no other registered format shares that two-letter prefix). Per the ticket's architectural note, `ChargeNormalized.unsupported_reason()` returns `Some(...)`, so the generic one-spectrum `conversion::convert`/`workflow::render`/CLI path reports it as unsupported (exactly like PRO/RBS/NRA/ERD already do) rather than being retrofitted to take a second spectrum.
- **Computation lives outside `convert`.** `gui_state::charge_normalized(spectrum, selection, monitor, calibration) -> Result<Vec<u8>, conversion::ConversionError>` (new) takes the target spectrum, its `Selection`, the monitor `Spectrum` directly, and the calibration, and does the actual division and byte-writing itself — it reuses `conversion::bounds` (now `pub(crate)`, was private) for range validation and the existing `channel_count` helper (used by ticket 04's `roi_statistics`) for parsing each channel's count text, rather than re-parsing it. `src/gui.rs`'s `on_convert` branches on `format == Format::ChargeNormalized` *before* spawning the conversion worker: that branch resolves the monitor spectrum from the "Monitor ADC/spectrum" dropdown, validates the calibration, and calls `gui_state::charge_normalized` directly in a loop over the selected spectra/output paths — bypassing `workflow::render`'s per-spectrum `conversion::convert` loop entirely for this one format, while still reusing `workflow::filenames` (naming) and `workflow::write` (writing), which don't call `convert` and were already generic. `git diff --stat -- src/workflow.rs src/main.rs` is empty, confirming neither was touched.
- **None vs. calibrated output.** `charge_normalized` always computes `count / monitor_total` (the dimensionless ratio); when `calibration.counts_per_uc` is `Some(cpu)` it additionally multiplies by `cpu` (scaling the ratio to counts-per-µC, since `monitor_total / cpu` is the monitor's implied integrated charge in µC). Covered by `charge_normalized_dimensionless_ratio_without_calibration` and `charge_normalized_scales_to_counts_per_uc_when_calibrated`, the second of which also asserts the calibrated output differs from the uncalibrated ratio (not just coincidentally equal).
- **Zero-count monitor is a structured error, not a divide-by-zero.** Added `ConversionError::MonitorNoCounts` (Display: exactly "monitor ADC recorded no counts") and `ConversionError::InvalidCount(String)` (wraps `channel_count`'s own diagnostic for unparseable count text) to the existing `conversion::ConversionError` enum, reusing the project's established structured-error type for this module rather than returning a loose `String`. `charge_normalized` sums the monitor's channels first and returns `Err(ConversionError::MonitorNoCounts)` before ever dividing, if that sum is `0.0`. Covered by `charge_normalized_reports_structured_error_for_zero_count_monitor`, which asserts both the exact variant (`matches!`-style `assert_eq!`) and its `Display` text.
- **Convert screen UI.** `ui/main.slint` gained `monitor-adcs: [string]` / `monitor-adc: int` / `counts-per-uc: string` properties and a `if root.mode == 8: VerticalLayout { ... }` section inside the existing "Conversion settings" panel — index 8 is `gui_state::MODES`'s new 9th entry, "Charge-normalized (µC)" (added alongside the other 8, following the ROI-rows/time-window-rows precedent for a conditionally-shown sub-panel keyed off a `root.mode`/`root.list-mode` check). `src/gui.rs`'s `monitor_adc_labels` (new) builds one "ADC{n} · {channels} channels" entry per loaded spectrum (`ui.set_monitor_adcs`/`ui.set_monitor_adc(0)` called wherever `ui.set_spectra` already is, for both the `.mpa` load path and the `.lst`-via-ticket-2-histogram Convert-screen load path, so the dropdown works identically for both file types as the ticket asked). The optional "Counts per µC" field is validated by the new `gui_state::charge_calibration(monitor_adc, text)`: blank parses to `None`; otherwise it must be a finite, positive `f64`, or the user sees a validation error before any worker thread spawns (matching the existing `gui_state::parameters` validate-then-spawn pattern).
- **Unit tests.** All three required cases are in `src/gui_state.rs`'s `tests` module, named with the `charge_normalized` prefix so `cargo test charge_normalized` selects exactly them: the dimensionless-ratio case, the counts-per-µC-scaled case (same spectrum/monitor pair, calibration added), and the zero-count-monitor structured-error case.

One pre-existing test outside this ticket's "Files to Touch" list needed a narrow, justified fix: `tests/gui_workflow.rs::mode_mapping_and_validation` asserted every `MODES` entry is supported through `conversion::convert` and used mode index `8` as its "out of range" probe — both assumptions break once `MODES` grows to 9 entries with `ChargeNormalized` deliberately unsupported through that generic path. Updated the assertion to allow `ChargeNormalized` as the one documented exception, and moved the out-of-range probe to index `9` (now the first invalid index), both with comments explaining why. No other test or non-ticket file needed changes.

## Blockers / Challenges

None. One deliberate design call worth flagging for review: `ConversionError::InvalidCount(String)` wraps `gui_state::channel_count`'s own message rather than being a fully independent structured variant (e.g. carrying `{ channel: usize, value: Vec<u8> }`). This only triggers on malformed count text in either spectrum, which `roi_statistics`/`spectrum_chart` already treat the same informal way (plain `String` errors) for every other feature that calls `channel_count`; a fully structured variant here would be inconsistent with that precedent for a failure mode the ticket's acceptance criteria don't actually exercise (only `MonitorNoCounts` is required to be structured, and it is, exactly).
